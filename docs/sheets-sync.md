# Google Sheets → Supabase 연결

상태: 전용 Supabase 프로젝트 생성 및 원본·정규화 자료의 최초 이관 완료. Google Sheets의 이후 수정분을 자동 반영하는 작업은 아직 배포하지 않았다.

## 기록의 기준

Google Sheets를 편집 원장으로 사용한다. Supabase의 비공개 수집 테이블은 승인된 행의 스냅샷과 변경 이력을 보관한다. 웹사이트에 공개하는 `public.buildings`는 별도의 공개 검수를 거친 데이터만 받는다. 동기화 성공은 공개 승인과 다르다.

- 원본 6개 탭: 최초 제공 자료를 수식·서식과 함께 보관한다.
- 건물·임대분기·개발·거래·임차이전 탭: 고정 UUID를 가진 편집 원장.
- 검수상태와 반영요청: `검수완료`이면서 `요청`인 행만 수집 대상으로 삼는다.
- 동기화상태·최종동기화: 성공한 DB 응답 이후에만 기록한다.
- 행번호는 식별자가 아니다. UUID가 비어 있거나 중복되면 중단한다. 행 삭제는 DB 삭제로 전파하지 않는다.
- 거래·이전의 연결건물ID는 명칭·권역 기반 후보이며 주소·동별 범위를 확인해야 한다.
- 원본의 빈칸·하이픈·0을 보존하며, 알려지지 않은 값을 0으로 채우지 않는다.

## 구현할 연결 지점

1. 별도 서버 작업 또는 Google Apps Script의 승인된 실행이 시트의 값과 고정 ID를 읽는다.
2. `검수완료 + 요청` 조건, UUID 중복, 숫자 단위와 헤더를 검증한다.
3. 서비스 전용 서버 인증으로 `record_sheet_batch` RPC를 호출한다. 공개 키·익명 사용자는 실행할 수 없다.
   비교·저장할 payload에서는 `동기화상태`와 `최종동기화` 같은 실행 결과를 제외한다. 결과를 시트에 기록한 것만으로 새 변경 이력이 생기지 않도록 한다.
4. DB는 같은 ID·같은 내용이면 이력을 늘리지 않고, 내용이 달라진 경우 새 revision을 기록한다.
5. 실행 전후 행 ID와 내용이 같은지 재확인하고 성공 상태·시각을 해당 ID의 행에 기록한다. 실행 중 수정되거나 이동해 안전하게 찾지 못하면 상태를 덮어쓰지 않는다.
6. 웹 공개 반영은 면적, 용도, 출처, 기준일, 개별 동과 거래 연결 검수 후 별도 수행한다.

자동 실행 주기는 프로젝트 연결 후 정한다. 현재 예약 실행이나 양방향 덮어쓰기는 없다. 비밀 키는 시트·프런트엔드·공개 저장소에 넣지 않는다.

## 데이터 파일

실제 원본·정규화 결과는 `data/private/`에 두며 Git에서 제외한다. 공개 저장소에는 변환 코드, 마이그레이션과 합성 데이터 테스트만 포함한다. `normalize-source.py`는 최초 스냅샷 정리용이고, 운영 시트의 UUID를 재발급하는 도구가 아니다.
