# 데이터 모델과 구현 단계

현재 마이그레이션은 서비스의 첫 데이터 연결을 위한 기반이다. 기획안 전체의 상세 DB가 완성된 상태를 의미하지 않는다.

## 현재 테이블

- `buildings`: 건물의 현재 공개 요약. 원본 면적, 실제/계획 기준, 좌표, 출처·확인일과 게시 상태. 1만 평 미만 원장은 보관할 수 있지만 공개할 수 없다.
- `building_facts`: 출처와 기준일을 갖는 확장 사실. 검증되지 않은 정보는 기본 비공개. 투자자 개인정보나 회사 내부자료를 넣지 않는다.
- `favorites`: 계정별 관심 건물. 본인만 조회·등록·삭제.
- `private.building_revisions`: 변경 이전 원장과 시점. 클라이언트 접근 불가.

## 세부 데이터 확장

임대료·공실·거래가·개발비는 단순 문자열이나 기준 없는 숫자로 공개하지 않는다. 다음 영역은 별도 정규화 테이블과 조회 화면을 함께 구현한다.

1. 면적 이력: 실제/계획, 산정 범위, 원문 값·단위, 확인 출처, 유효기간.
2. 임대 조건: 보증금, 월 임대료·관리비, 면적 기준, 통화, 부가세, 제안/체결 구분, 렌트프리 기간. NOC는 산식과 입력값·가정을 명시.
3. 공실: 분자·분모·대상 범위·기준일 일치. 미확인과 0을 구분.
4. 소유·운용·임차: 법인과 역할·유효기간. 복수 빌딩 거래는 거래와 건물의 다대다 관계 및 금액 배분 여부 보존.
5. 개발: 프로젝트와 건물 연결, 계획 버전, 인허가·착공·준공 이력, 사업비 범위와 기준일.
6. 출처·검증: 필드별 증거, 최신성, 정정 이력. 접근 권한별 공개 데이터 분리.

## 연결 후 확인 항목

빈 전용 프로젝트에서 마이그레이션 적용 → 공개/비공개·면적 경계값 확인 → 익명 수정 차단 확인 → 서로 다른 두 계정 간 관심 건물 격리 확인 → 실출처가 확인된 첫 건물 등록 → 실제 지도 좌표·인증 허용 URL 확인.

로컬 PGlite 테스트에서 마이그레이션 실행, 공개 면적 기준, 익명 수정 차단, 두 계정 간 관심 건물 격리 및 비공개 이력을 검증한다. 연결 후 실제 Supabase API·Auth와 네이버 지도 인증을 별도로 확인한다.

## 자산 아카이브 화면과 전용 테이블

- 전체 매매사례: 검색, 권역·연도·매입범위 필터, 최근순/금액순, 20건 단위 페이지, 거래 상세 → 자산 상세 연결.
- 자산 상세: 개요 / 임대 정보 / 임차기업 / 거래 이력 / 개발·변경 이력. 관심 건물과 기존 비교 기능 유지.
- `transactions`: 원문 연도 정밀도, 전체 연면적과 실제 거래면적, 원문 평당가를 분리. 후보 링크는 공개할 수 없다.
- `transaction_assets`: 묶음 거래의 추가 자산과 명시적 금액 배분을 보관하는 확장 테이블. 현재 화면은 거래의 대표 자산을 연결하며, 미배분 금액으로 개별 자산 평당가를 만들지 않는다.
- `companies` + `occupancies`: 법인과 입주 기록 분리. 현재 입주 확인, 과거, 미확인 구분. 종료된 기록은 현재 기업 수에 포함하지 않는다. 기업 목록·층별 보기·기업별 건물 이동 지원.
- `tenant_movements`: 과거 이전 사례 전용. 현재 입주 현황으로 자동 변환하지 않는다.
- `leasing_quarters`, `development_records`: 분기별 임대 수치와 개발 기록. 자료가 없는 값을 0으로 대체하지 않는다.
- `private.source_snapshots`: 제공 자료와 정규화 결과의 최초 스냅샷. 웹 클라이언트에서는 접근할 수 없다.
- `private.reviewers`: 확인된 이메일의 검수자 허용 목록. 이메일 인증 완료된 계정만 미공개 원장을 읽을 수 있다. 공개 변경 권한은 부여하지 않는다.

개발 서버는 원본 로컬 파일을 읽지 않는다. 화면 데이터는 Supabase Data API만 사용한다. 비로그인 방문자는 검수·게시 완료된 자료만 보고, 검수 계정은 원본 기준일과 미검수 상태가 표시된 초안을 본다. 시트 자동 동기화 작업은 아직 배포하지 않았다.
