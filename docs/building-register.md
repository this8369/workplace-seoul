# 건축물대장 데이터 관리

출처: [국토교통부 건축HUB 건축물대장정보 서비스](https://www.data.go.kr/data/15134735/openapi.do).
2026-09-21 공개 API 명세 및 실제 응답으로 확인. API 인증키는 서버에서만 사용한다.

## 저장 구조

- `private.building_register_snapshots`: API 기능별 요청 지번, 전체 페이지 원본, 수집시각, 내용 해시. 인증키와 키가 포함된 URL은 저장하지 않는다. 원본 버전은 누적 보관한다.
- `public.building_register_records`: 표제부/총괄표제부 정규화. `(register_pk, record_kind)`로 식별. `record_kind=complex`와 `building`을 구분한다.
- `public.building_register_links`: 기존 자산 및 선택적 개별 동 연결, 검증 상태, 검증 근거/시점. 주소가 같다는 이유만으로 자동 승인하지 않는다.
- `public.building_register_floors`: 한 층에 여러 용도별 행이 있을 수 있으므로 원본 항목 순번을 보존한다.
- `public.building_register_area_parts`: 전유/공용 구분별 면적. 호별 대장 PK가 표제부 PK와 직접 일치하지 않는 자료는 원본에 보존하고 연결을 보류한다.
- `public.building_register_sections`: 지역지구/오수정화의 항목명을 정규화한 JSON. 원본 전체는 private에서 별도 관리한다.

각 정규화 자료가 원본 snapshot을 참조한다. 데이터는 PostgreSQL/Supabase에 저장하고, 프런트엔드는 자산 상세의 ‘건축물대장’ 탭을 열 때만 조회한다. 전체 지도 로딩에 층별 대장을 함께 내려보내지 않는다.

## 식별·면적 원칙

1. 시군구 5자리 + 법정동 5자리 + 대지구분 + 본번 4자리 + 부번 4자리를 문자열로 유지한다. 도로명 법정동코드와 지번 법정동코드를 혼용하지 않는다.
2. 대장 PK, 자산의 주소·명칭·면적, 실제 동 구분을 검토한 연결만 상세페이지에 표시한다. 기존 자산이 비공개면 연결된 대장도 익명 사용자에게 노출하지 않는다. 일반 로그인만으로 검수 권한이 생기지 않는다.
3. 단지 총괄 연면적과 동별 연면적을 합산하지 않는다. 한 대장을 임대 마케팅상의 A/B 구분마다 복제하지 않는다.
4. 면적은 원본 ㎡로 저장한다. 층별 건축면적이나 전유/공용 합계를 기준층 임대·전용면적으로 자동 대입하지 않는다. NOC, 사용자 입력 기준층, 개발 계획면적은 변경하지 않는다.
5. 실제 층별 용도 내역은 건축물대장 원천 자료이다. 서비스에서 없앤 저층부/중층부/고층부 임대 구획을 재생성하지 않는다.
6. 개발사업 부지의 기존 건물대장을 신규 개발건의 준공 정보로 연결하지 않는다. 현재 importer는 운영자산의 검증 링크만 허용한다.
7. 빈 값은 null, 실제 0은 0으로 구분한다. 유효하지 않은 날짜와 연도만 있는 날짜는 날짜를 만들어 채우지 않고 원본에 보존한다. API 원본 0 값도 실측 검증을 의미하지 않는다.
8. 수집일과 원천 생성일을 구분한다. 생성일을 현행성 보장일로 사용하지 않는다.

## 실행

환경변수 `BUILDING_REGISTER_SERVICE_KEY` 또는 git-ignore된 `data/private/building-register-key`에서 인증키를 읽는다. `VITE_` 환경변수나 공개 GitHub 파일에 넣지 않는다.

```sh
node --use-system-ca scripts/building-register/probe.mjs
node --use-system-ca scripts/building-register/collect.mjs data/private/building-register-plan.json
node --use-system-ca scripts/db/apply.mjs
node --use-system-ca scripts/building-register/import.mjs data/private/building-register-plan.json
node --use-system-ca scripts/building-register/import.mjs data/private/building-register-plan.json --apply
```

`collect`는 지번별 조회를 순차 실행하며 24시간 캐시, 페이지네이션, 타임아웃을 적용한다. `--refresh`로 갱신한다. API 오류와 조회결과 0건을 구분한다. 실패하면 오류 메시지에 인증키/전체 URL을 출력하지 않는다.

`import` 기본값은 트랜잭션 롤백 검증이다. `--apply`에만 저장한다. 모든 요청 지번·반환 지번 및 내용 해시를 검증하고, 대장·층별 데이터와 검증 링크를 하나의 트랜잭션에서 갱신한다. 같은 수집본의 재실행은 중복 원본을 만들지 않는다. 성공한 전체 응답에 한해 해당 기능의 이전 정규화 항목을 교체한다. 사라진 표제부는 `is_current=false`로 보존한다. 실패한 조회는 기존 데이터를 지우지 않는다. 원본은 변경 전 버전까지 남는다.

비공개 계획 파일의 `parcels`에 지번 코드를 입력하고 `operations`로 수집 기능을 지정한다. `links`에는 검토한 `building_id`, `expected_building_name`, `register_pk`, `record_kind`, `parcel_key`, `expected_register_name`, `evidence` 및 필요시 `tower_id`를 지정한다. 자산 ID를 모르는 원천은 원본과 정규화 대장만 저장해 두고 연결을 추후 검증할 수 있다.

## 최초 연결 범위

그랜드센트럴(남대문로5가 831)을 대상으로 8개 API 기능을 수집했다. 표제부 1건, 층별 용도·면적 51항목, 지역지구 4항목, 오수정화 3항목을 확인했다. 총괄표제부·전유공용면적·부속지번은 0건 응답을 기록했다. 전체 자산 일괄 수집이 완료된 상태는 아니다.
